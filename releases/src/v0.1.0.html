pspt — spec-driven development for Claude Code

Requirements and a static mockup go in; the engineering specification set comes out — then the build loop runs against it.

Two gates, then one stage per invocation

brd · prd · srs+ mockup/*.html, every state drawn
→
Gate 1 · completeall four inputs present
→
Gate 2 · consistentrequirements ⇄ mockup, both ways
→
S2data spec + ERD
·
S3rules, errors, stack
·
S4endpoints, tests
·
S5screens
·
S6phases.md

A gap in either gate stops everything: either a complete, traceable document set, or a list of what disagrees — never a half-spec.

The build loop

phases.mdone exit criterion
→
REDtest first, fails for the right reason
→
GREENminimum code
→
CLEANrefactor, tests stay green
→
CHECKwhole tree, zero warnings

Six skills · fixed conventions

  • /pspt:status — where the project stands, read-only
  • /pspt:spec — the next stage of the specification set
  • /pspt:build — one criterion through red → green → clean → check
  • /pspt:trace — requirement → screen → column → endpoint → test
  • /pspt:code — an error code in every place it must appear
  • /pspt:reg — a numbered regression, wired into the specs
  • TypeScript, feature-based architecture — fixed, never asked
  • A pure *.rules.ts decision layer the linter enforces — no I/O, no Date, no fetch
  • Stack asked in dependency order, each answer deleting later questions
  • Lint rules selected from references/lint/ — Express, NestJS, Next.js, React — never authored
